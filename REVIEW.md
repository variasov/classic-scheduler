# Ревью classic-scheduler 1.4.1

Ревью от 2026-11-04 по ветке `main` (`e4ce921`). Код совпадает с версией 1.4.1 на PyPI.
Проверка: чтение кода, пробы на Python 3.14, pyright strict.

Зависимость `classic-actors` (базовый класс `Actor`) разобрана в её собственном `REVIEW.md`.
Часть ошибок планировщика исправляется там.

## Замечания к коду

1. **`stop()` не останавливает планировщик, запущенный через `run()`.** [высокая]
   - Где: `Actor.stop()` (`classic-actors`, `actor.py:89-94`) кладёт `Stop` в очередь, только если `is_alive()`.
     `is_alive()` смотрит на поток, созданный `start()`. Если `run()` вызван в своём потоке, `_thread is None`.
   - Последствие (проверено): `stop()` ничего не делает, цикл крутится дальше.
     Так запускают планировщик в `__main__` процесса, это основной сценарий.

2. **После `stop()` планировщик нельзя запустить снова.** [средняя]
   - Где: `scheduler.py:96-98` — `_after_loop` закрывает `ThreadPoolExecutor`, а создаётся он один раз в `__init__`.
   - Последствие (проверено): после `start()` → `stop()` → `start()` поток падает с
     `RuntimeError: cannot schedule new futures after shutdown`.

3. **Cron считается в UTC, и это нигде не сказано.** [высокая]
   - Где: `task.py:97` — `croniter(schedule, datetime.now(timezone.utc))`.
   - Последствие (проверено): `'0 9 * * *'` срабатывает в 09:00 UTC, а не по местному времени.
     Параметра часового пояса нет.

4. **Имена задач в `register` строятся из `id(obj)`, а не из метода.** [средняя]
   - Где: `scheduler.py:217-247`. В `_task_name_for_method` передаётся `obj`, хотя параметр называется `method`.
   - Последствие: два метода одного объекта с одинаковым расписанием получают одно имя,
     `unregister` или `cancel` снимает оба.
   - Там же лишний вызов `self._task_name_for_method(obj, schedule)`, результат которого не используется (`:230`, `:246`).

5. **Имя задачи по умолчанию — `job.__qualname__`.** [средняя]
   - Где: `task.py:24`.
   - Последствие: все лямбды называются `<lambda>`, все экземпляры одного метода — `Cls.method`.
     `cancel('<lambda>')` снимает все такие задачи разом; при этом пользователь имени не задавал и не знает его.

6. **Запуски одной задачи перекрываются.** [средняя]
   - Где: `scheduler.py:60-70`, `90-94` — следующий запуск планируется до выполнения текущего.
   - Последствие: при `workers_num > 1` задача, которая работает дольше периода, выполняется параллельно сама с собой.
     При `workers_num = 1` запуски копятся в очереди пула. Нигде не описано.

7. **Поток планировщика — daemon.** [средняя]
   - Где: `Actor.start()` (`classic-actors`, `actor.py:84`), там же TODO.
   - Последствие: при выходе процесса задача обрывается на середине.

8. **Типизация.** [средняя]
   - Нет `py.typed`: pyright strict в пользовательском коде даёт `reportUnknownMemberType` на `by_cron`/`by_period` (проверено).
   - `args: tuple = None`, `kwargs: dict = None`, `task_name: str = None` — без `Optional` и параметров типов.
   - `job: Callable[[...], None]` (`task.py:16`) — неверная запись, должно быть `Callable[..., Any]`.
   - `job: Callable[[], None]` в `with_delay` при наличии `args`/`kwargs` — сигнатура противоречит использованию.
   - `next_run_time -> datetime`, хотя бывает `None` (`OneTimeTask`).
   - Декораторы `by_cron`/`by_period` объявлены как `-> Method` со свободным TypeVar, хотя возвращают декоратор.
   - `__init__.py` без `__all__`.

9. **Логирование в корневой логгер.** [низкая]
   - Где: `task.py:53-68` — `logging.info(...)`, `logging.exception(...)`.
   - Последствие: нельзя настроить уровень для планировщика отдельно; `logging.info` на корневом логгере
     ещё и вызывает `basicConfig`, если логирование не настроено.

10. **`_calc_next_task_execute_time` без задач ждёт 60 секунд.** [низкая]
    - Где: `scheduler.py:47-48`. На поведение не влияет (новая задача приходит через очередь), но число магическое.

11. **Тесты.** [средняя]
    - Тесты держатся на `time.sleep` с запасом в десятки миллисекунд — нестабильны под нагрузкой.
    - `datetime.utcnow()` (`tests/test_scheduler.py:88`) устарел с Python 3.12.
    - Нет тестов на `stop()` после `run()`, повторный запуск, `register`/`unregister`, перекрытие запусков, ошибку в задаче.

## Замечания к документации (README.md)

- `@component def SomeLogic:` — синтаксическая ошибка, должно быть `class`.
- В разделе «Параметризация» `scheduler.run()` вызывается до `by_period(...)`; `run()` блокирует поток навсегда, код ниже не выполнится.
- Описаны параметры `block` и `timeout` у `stop()` — их нет.
- Пример `cancel` повторяется дважды подряд.
- Опечатки: «Переодическая», «выполнятmся», «задач» вместо «задачи».
- Не описано: что cron в UTC; формат cron (5 или 6 полей — `croniter` поддерживает секунды, тесты используют 6 полей);
  что запуски перекрываются; как формируется имя задачи по умолчанию; что ошибки задачи логируются и не останавливают планировщик;
  что `by_period` выполняет задачу сразу при добавлении.

### Решения (2026-11-04)

- Отказаться от зависимости `classic-actors`: цикл, очередь команд, `start`/`run`/`stop`/`join`/`is_alive`
  переносятся в сам `Scheduler`. Задачи 1 и 7 из `classic-actors/REVIEW.md` (stop при `run()`, daemon-поток)
  решаются здесь. `Scheduler` перестаёт быть `Actor` — его нельзя будет передать в `classic.actors.Supervisor`.
- Убрать интеграцию с `classic-components`: декораторы `by_cron`/`by_period`, `register`/`unregister`, наследование `Registry`.
- Изменения поведения (локальный пояс cron, пропуск перекрывающихся запусков, отказ от `Actor`) — мажорная версия 2.0.0.
